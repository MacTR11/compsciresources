### Activity 4 — Justifications

**(a)** Binary search is O(log n) because **each comparison halves the size of the list still to be searched** — it discards the half that cannot contain the target. The number of times n can be halved before reaching 1 is log₂(n), so the number of comparisons grows logarithmically with n. (Doubling the list size adds only one extra comparison.)

**(b)** Bubble sort is O(n²) because it uses **two nested loops**: an outer loop of up to n passes, and for each pass an inner loop making up to n adjacent comparisons. That gives roughly n × n = n² comparisons, so time grows with the square of the input size.

**(c)** Binary search requires the list to be **sorted**; linear search works on unsorted data.

### Challenge

**(a)** A heuristic is **admissible** if it **never overestimates** the true shortest-distance from a node to the goal F. To check, compare each h(n) to the actual shortest distance to F (computed by Dijkstra from each node):
- True shortest distances to F — F:0, E:3, D:5 (D→E→F = 2+3), B:10 (B→D→E→F = 5+2+3), C:11 (C→B→D→E→F = 1+5+2+3), A:13.
- Heuristic given: A=9, B=7, C=8, D=4, E=3, F=0. Each is ≤ the true distance (9≤13, 7≤10, 8≤11, 4≤5, 3≤3, 0≤0), so the heuristic **is admissible** and A* would find the optimal path.

**(b)** A* explores fewer nodes than Dijkstra when a **good (informative) heuristic** directs the search toward the goal instead of expanding outward in all directions — useful when you only need the path to **one** goal node. A* behaves **exactly like Dijkstra** when the heuristic is **h(n) = 0** for every node (no information), because then f(n) = g(n).

### Activity 8 — A* vs Dijkstra

Edges: S-A 1, S-B 4, S-D 2, A-B 2, A-C 5, B-C 2, C-G 3. Heuristic: h(S)=7, h(A)=6, h(B)=4, h(C)=3, h(D)=9, h(G)=0.

**(a) Dijkstra from S:**

| Settled (order) | S | A | B | C | D | G |
|-----------------|---|---|---|---|---|---|
| Initial | 0 | ∞ | ∞ | ∞ | ∞ | ∞ |
| Settle S (0) | 0 | 1 | 4 | ∞ | 2 | ∞ |
| Settle A (1) | 0 | 1 | 3 | 6 | 2 | ∞ |
| Settle D (2) | 0 | 1 | 3 | 6 | 2 | ∞ |
| Settle B (3) | 0 | 1 | 3 | 5 | 2 | ∞ |
| Settle C (5) | 0 | 1 | 3 | 5 | 2 | 8 |
| Settle G (8) | 0 | 1 | 3 | 5 | 2 | 8 |

Relaxations: from S: A=1, B=4, D=2. Settle A(1): B=min(4, 1+2)=3, C=1+5=6. Settle D(2): only neighbour S already settled — **no updates**. Settle B(3): C=min(6, 3+2)=5. Settle C(5): G=5+3=8. Settle G(8).

Settle order: **S → A → D → B → C → G** (all 6 nodes; Dijkstra settles the dead-end D third).

**(b) A\* from S:**

| Node expanded | g(n) | h(n) | f(n) |
|---------------|------|------|------|
| S | 0 | 7 | 7 |
| A | 1 | 6 | 7 |
| B | 3 | 4 | 7 |
| C | 5 | 3 | 8 |
| G | 8 | 0 | 8 |

Working: expand S → open list A(f=1+6=7), B(f=4+4=8), D(f=2+9=11). Expand A(7) → B improves to g=3, f=7; C added g=6, f=9. Expand B(7) → C improves to g=5, f=8. Expand C(8) → G added g=8, f=8. Expand G(8) = goal, stop.

Shortest path S → G: **S → A → B → C → G**, distance **8** (1+2+2+3 = 8; alternatives S→B→C→G = 4+2+3 = 9 and S→A→C→G = 1+5+3 = 9 are longer ✓).

**(c)** **D**. Its f value is `f(D) = g(D) + h(D) = 2 + 9 = 11`, which is **higher than the f of every node on the route to the goal** (all ≤ 8). Because A* always expands the lowest-f node and reaches G at f = 8, D is never the best choice — the heuristic signals that D is heading **away** from the goal, so A* never wastes time expanding it. (The heuristic is admissible: each h(n) ≤ the true distance to G — S 7≤8, A 6≤7, B 4≤5, C 3≤3, D 9≤10, G 0≤0 — so A*'s answer is still optimal.)

**(d)** Satnav (one start, one destination, straight-line distances available): **A\*** — the admissible heuristic focuses the search towards the destination, so it typically expands **fewer nodes** than Dijkstra for a single goal. Network-monitoring tool (shortest routes to **every** node): **Dijkstra** — it naturally computes shortest distances to **all** nodes in one run, and no single-goal heuristic exists when every node is a target.

**Q4 (5 marks).** Model answer:

```
function searchIndex(arr:array, n, target)
    low = 0
    high = n - 1
    while low <= high
        mid = (low + high) DIV 2
        if arr[mid] == target then
            return mid
        elseif arr[mid] < target then
            low = mid + 1
        else
            high = mid - 1
        endif
    endwhile
    return -1
endfunction
```

Mark points (one each):
- Function declaration with the three parameters; `low`/`high` pointers **initialised** to 0 and n − 1. **[1]**
- Loop that continues **while low <= high**. **[1]**
- Midpoint calculated with **integer division**: `mid = (low + high) DIV 2`. **[1]**
- Correct **narrowing** of the search range: `low = mid + 1` when `arr[mid] < target`, `high = mid - 1` when it is greater. **[1]**
- **Returns `mid`** when the target is found and **returns -1** after the loop when it is not. **[1]**

**Model top-band answer:**

**Searching.** The 50 million records are stored **in order of track ID**, which is the precondition for **binary search**. Binary search is **O(log n)**: each comparison halves the remaining search space, so a lookup needs at most about log₂(50,000,000) ≈ **26 comparisons**, compared with up to 50 million for a **linear search (O(n))**. At thousands of searches per second, linear search would be completely infeasible, so binary search should be used everywhere the data is sorted — including the car system's list of downloaded tracks.

**Nightly sort on the server.** For 50 million records, an **O(n²)** algorithm such as bubble or insertion sort is unusable (≈ 2.5 × 10¹⁵ comparisons), so an **O(n log n)** algorithm is needed. **Merge sort** is the best choice for the server: its worst case is **guaranteed O(n log n)** (unlike quicksort, which degrades to **O(n²)** on unluckily ordered data — a risk when the input is already mostly sorted), so the nightly job will reliably finish inside its time window. Merge sort's drawback is **O(n) auxiliary space** for the temporary merge lists, but the scenario states the server has a large amount of memory, so this cost is acceptable. Better still, the developers can exploit the structure of the data: the existing 50 million records are **already sorted** and only a few thousand new tracks arrive. Sorting just the small batch (n log n on a few thousand items) and then performing a **single O(n) merge pass** into the main file is far cheaper than re-sorting everything — exactly the merge step of merge sort.

**Embedded car system.** Here memory is the constraint, so merge sort's O(n) extra space is a poor fit. With only a few hundred tracks, an **in-place** algorithm with **O(1) auxiliary space**, such as **insertion sort**, is appropriate: although it is O(n²) in the average/worst case, n is tiny so the time is negligible, and insertion sort runs in close to **O(n)** when new tracks are inserted into an already-sorted list — the common case here. (An in-place quicksort would also be acceptable.)

**Conclusion:** binary search (O(log n)) for all lookups on the sorted data; merge sort — ideally sort-the-batch-then-merge — for the nightly server job because its guaranteed O(n log n) time matters more than its O(n) space there; and in-place insertion sort on the embedded device, where O(1) space matters more than asymptotic speed on a few hundred items.
